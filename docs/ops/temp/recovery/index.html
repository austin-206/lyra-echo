    Disaster Recovery Runbook (Lyra / Deb / MirrorPi / Raspi)¶

    This runbook documents the end-to-end restoration procedure for any host in the the Lyra–Sulafat constellation using BorgBackup.

    It is designed for real emergencies:

    • Disk failure
    • OS corruption
    • Misconfiguration
    • Accidental deletion
    • Compromise requiring full rollback

    Borg repositories are stored on Sulafat (10.0.0.74) in NFS export directories mounted at:

    /mnt/unas/<hostname>

    You must have:

    • The encrypted Borg repository on Sulafat
    • The exported Borg key for the affected host
    • The Borg passphrase

    Without those, recovery may not be possible.

    1. Repositories and Hosts¶

    Each host has a corresponding repository on Sulafat:

    Host Repository path
    Lyra /mnt/unas/lyra
    Deb /mnt/unas/deb
    MirrorPi /mnt/unas/mirrorpi
    Raspi /mnt/unas/raspi

    The backup runbooks for each host (e.g., backups/lyra.md) describe how these repos are populated.

    2. Restore Scenarios¶

    There are two main restore scenarios. The steps differ depending on the state of the target disk.

    2.1 Scenario A — Disk and Partitions Intact (Preferred)¶

    Use this when:

    • The host’s disk and partition layout still exist
    • The root filesystem is present but the OS is broken, corrupted, or compromised
    • You want to fully roll back to a previous state

    In this case, you do not reinstall the OS.
    You boot from external media, mount the existing partitions, and restore onto them.

    2.2 Scenario B — Disk New / Replaced / Empty¶

    Use this when:

    • The host’s disk has been replaced
    • The partition table is gone
    • There is no filesystem for Borg to restore into

    In this case, you perform a minimal OS install first to recreate:

    • The partition table
    • The EFI/boot partition (if applicable)
    • The root filesystem

    Then, you overwrite that fresh install with the Borg restore.

    3. Common Requirements for Both Scenarios¶

    Regardless of scenario:

    1. Network access to Sulafat (10.0.0.74)
    2. Ability to mount the NFS export: 
      /mnt/unas
    3. BorgBackup installed on the environment you are using to restore
    4. Borg key and passphrase available

    NFS export (conceptual):

    10.0.0.74:/volume/<uuid>/.srv/.unifi-drive/Storage/.data  →  /mnt/unas

    Inside /mnt/unas, each host’s Borg repo lives in its own subdirectory.

    4. Scenario A — Restore with Existing Disk (Lyra Example)¶

    This is the preferred method when the disk is intact.

    We’ll use Lyra as the example; Deb and others are analogous with different device names.

    4.1 Boot from Live USB¶

    1. Insert an Ubuntu Live USB.
    2. Boot Lyra and choose “Try Ubuntu” (do not install).

    You are now in a temporary OS running from USB/RAM.

    4.2 Identify Lyra’s Partitions¶

    Open a terminal and run:

    lsblk -f

    Find:

    • Root partition (e.g., /dev/nvme0n1p2, type ext4)
    • EFI partition (e.g., /dev/nvme0n1p1, type vfat)

    4.3 Mount Lyra’s Root and EFI¶

    sudo mkdir -p /mnt/target
sudo mount /dev/nvme0n1p2 /mnt/target

sudo mkdir -p /mnt/target/boot/efi
sudo mount /dev/nvme0n1p1 /mnt/target/boot/efi

    Now /mnt/target is Lyra’s future /.

    4.4 Mount Sulafat’s NFS Export¶

    sudo mkdir -p /mnt/unas
sudo mount -t nfs 10.0.0.74:/volume/<uuid>/.srv/.unifi-drive/Storage/.data /mnt/unas

    Verify:

    df -hT | grep unas
ls /mnt/unas

    You should see lyra, deb, mirrorpi, raspi, etc.

    4.5 Install Borg in the Live Environment¶

    sudo apt update
sudo apt install borgbackup
borg --version

    4.6 Select an Archive to Restore¶

    List Lyra’s archives:

    borg list /mnt/unas/lyra

    Example output:

    lyra-2025-12-07_13-50-40   Sun, 2025-12-07 13:50:43
lyra-2025-12-08_03-30-00   Mon, 2025-12-08 03:30:00
...

    Choose an appropriate snapshot (usually the most recent known-good).

    4.7 Restore the Filesystem into /mnt/target¶

    From the live environment:

    sudo borg extract /mnt/unas/lyra::lyra-2025-12-07_13-50-40 --target /mnt/target

    Or, if using older Borg syntax:

    cd /mnt/target
sudo borg extract /mnt/unas/lyra::lyra-2025-12-07_13-50-40

    This reconstructs the entire OS onto Lyra’s root partition.

    4.8 Prepare for chroot and Reinstall GRUB¶

    Bind-mount essential system directories:

    sudo mount --bind /dev /mnt/target/dev
sudo mount --bind /proc /mnt/target/proc
sudo mount --bind /sys /mnt/target/sys

    Chroot into the restored system:

    sudo chroot /mnt/target

    Install GRUB to the disk:

    grub-install /dev/nvme0n1
update-grub

    Exit chroot:

    exit

    4.9 Clean Up and Reboot¶

    sudo umount -R /mnt/target
sudo umount /mnt/unas
sudo reboot

    Remove the USB when prompted or after shutdown.

    Lyra should now boot into the restored OS corresponding to the chosen archive.

    5. Scenario B — Restore to a New / Blank Disk (Lyra Example)¶

    Use this when:

    • Lyra’s disk has been replaced
    • There are no partitions or filesystems

    This scenario uses the OS installer only to create partitions and a minimal system, which is then overwritten by Borg.

    5.1 Minimal OS Install¶

    1. Boot from the Ubuntu installer.
    2. Install Ubuntu to the new disk using a simple layout:
    3. EFI partition (e.g., /dev/nvme0n1p1)
    4. Root partition (e.g., /dev/nvme0n1p2)
    5. Create one admin user.
    6. Boot into this fresh system once to confirm it works.

    You now have:

    • A valid GPT + EFI setup
    • A bootable, minimal Ubuntu install
    • A root filesystem to restore onto

    5.2 Install NFS and Borg on the Fresh OS¶

    sudo apt update
sudo apt install nfs-common borgbackup

    Create mountpoint:

    sudo mkdir -p /mnt/unas

    Mount Sulafat:

    sudo mount -t nfs 10.0.0.74:/volume/<uuid>/.srv/.unifi-drive/Storage/.data /mnt/unas

    Verify:

    ls /mnt/unas/lyra

    5.3 Mount the Root Filesystem at /mnt/target (If Needed)¶

    If you are already running from the installed OS, the root filesystem is /.
    For safety and clarity, you can still mount it via another live session, or simply use / as the restore target after booting from a Live USB as in Scenario A.

    Safer approach:
    Reboot into a Live USB and follow Scenario A, since the partitions now exist.

    In that case, once partitions are there, continue with Scenario A starting from:

    • “Identify Lyra’s Partitions”
    • “Mount Root and EFI”
    • “Mount Sulafat”
    • “Install Borg”
    • “Restore with borg extract”
    • “Reinstall GRUB”

    The key difference for Scenario B is just how the disk and partitions were created (via installer), not how Borg is used.

    6. Deb, MirrorPi, and Raspi¶

    The same two scenarios apply to Deb, MirrorPi, and Raspi, with different device names and OSes.

    6.1 Deb (Debian)¶

    • Boot medium: Debian live ISO or installer (rescue mode)
    • Root device: typically /dev/nvme0n1p2
    • EFI: /dev/nvme0n1p1
    • Repo: /mnt/unas/deb

    The restore steps are the same as Lyra, substituting:

    • Partition names
    • Repository path (/mnt/unas/deb)
    • GRUB install target (e.g., /dev/nvme0n1)

    6.2 MirrorPi and Raspi (Raspberry Pi OS)¶

    Raspberry Pi hardware typically boots from:

    • microSD, or
    • NVMe/USB with Pi firmware

    For Pi-based hosts:

    • Boot medium: Raspberry Pi OS imager or Pi OS live image
    • Restore is usually Scenario B style:
    • Flash Pi OS to disk
    • Boot Pi OS
    • Install nfs-common and borgbackup
    • Mount /mnt/unas
    • Use Borg to restore onto the root filesystem (either in-place or via chroot if using an external host)

    Pi boot does not use GRUB; the Pi firmware loads the kernel directly from /boot.
    If boot issues occur after restore, re-flashing /boot from a known-good Pi OS image and then restoring everything except /boot can be a practical compromise.

    7. Post-Restore Tasks (Per Host)¶

    After any full restore, perform host-specific checks.

    7.1 Lyra¶

    • Verify /mnt/data1 and /mnt/data2 mount correctly.
    • Reinstall or resync:
    • Model weights (Ollama, vLLM, Parler-TTS, etc.)
    • Containers that were intentionally excluded from backups.
    • Confirm gateway, Qdrant, and any orchestration services start.
    • Verify hostname and network configuration.

    7.2 Deb¶

    • Confirm /mnt/sec-onion mounts.
    • Verify Docker / Podman stacks:
    • Nextcloud
    • Postgres
    • MQTT
    • Node-RED
    • Security Onion / other services
    • Rebuild large images that were excluded.

    7.3 MirrorPi¶

    • Verify MagicMirror starts.
    • Confirm Lyra/Echo chat interface is reachable.
    • Check presence sensor integrations and any local services.

    7.4 Raspi¶

    • Confirm Pi-hole / DNS / DHCP are functioning.
    • Verify network services (static leases, upstream DNS).
    • Validate that other hosts can resolve names and reach the internet as expected.

    8. Verification Checklist (All Hosts)¶

    After a restore:

    System-Level¶

    • [ ] Host boots successfully from internal storage
    • [ ] Hostname is correct
    • [ ] Network connectivity to LAN and Sulafat

    Data-Level¶

    • [ ] All expected mountpoints present (/mnt/data1, /mnt/data2, /mnt/sec-onion, etc.)
    • [ ] Filesystems have expected size and usage

    Application-Level¶

    • [ ] Core services started (per host)
    • [ ] Lyra gateway responds and can answer queries
    • [ ] Mirror UI loads and reacts to presence
    • [ ] Raspi resolves DNS correctly for other devices

    Backup-Level¶

    • [ ] NFS mount to /mnt/unas restored in /etc/fstab
    • [ ] borg list /mnt/unas/<host> works
    • [ ] Nightly backup cron jobs present
    • [ ] Borg key and passphrase stored safely off-host

    9. Testing a Restore (Non-Destructive)¶

    At least periodically, perform a dry-run restore test on non-production hardware:

    1. Spin up a VM or attach a spare disk.
    2. Create minimal partitions and install a base OS (if using Scenario B).
    3. Mount Sulafat.
    4. Install Borg.
    5. Restore an archive for one host into that environment.
    6. Attempt to boot it (if bare-metal) or inspect files (if VM).
    7. Validate critical configs and data exist.

    This proves the backups are usable and the runbook is accurate.

    10. Failure Modes and Responses¶

    “Repository key mismatch”¶

    • The wrong Borg key file is being used, or the repo is not the one you think it is.
    • Re-check that the correct repo path and key file are used.
    • Re-import key if necessary: 
      borg key import /mnt/unas/<host> <keyfile>

    “Incorrect passphrase”¶

    • The passphrase is required; there is no bypass.
    • Check password manager or stored records.

    “NFS access denied”¶

    • Sulafat NFS export does not permit this host’s IP.
    • Update NFS client list / permissions on Sulafat GUI for:
    • Lyra
    • Deb
    • MirrorPi
    • Raspi
    • Retry the mount.

    “System fails to boot after restore”¶

    • Re-check:
    • GRUB install target (/dev/nvme0n1, not a partition)
    • EFI partition mounted correctly during chroot
    • update-grub output for correct root UUID
    • For Pi: ensure /boot partition has valid firmware + kernel.

    “Filesystem full”¶

    • The target disk must be at least as large as the original, or Borg may not be able to fully restore.
    • Resize or choose a larger disk.

    11. Conclusion¶

    This runbook provides a complete, scenario-based workflow for restoring:

    • Lyra
    • Deb
    • MirrorPi
    • Raspi

    from Borg backups stored on Sulafat.

    Use:

    • Scenario A when the disk and partitions exist (preferred, simpler).
    • Scenario B when the disk is new or has been wiped (installer used only to bootstrap partitions and bootloader).

    For host-specific backup configuration, see the corresponding backups/<host>.md documents.
