# 25 November 2025: New Sources of Information

## Context  
NOAA’s weather data illustrated its practical limits for the project when a test user queried it for weather in Reykjavik. The lack of global coverage and frequent inconsistencies demonstrated a need for a transition to modern and globally capable providers. The aim for this session was to replace NOAA with <a href="https://open-meteo.com/">Open-Meteo</a> and <a href="https://openweathermap.org/api">OpenWeather</a>, giving Lyra the ability to answer weather questions reliably for any location.

What began as a straightforward provider swap exposed broader architectural issues that had been accumulating in the background. This has provided an introduction to the complexity of necessary structure and controls needed to achieve expected output when develping a generative system. 

---

## Work Completed
Today's task was integrating Open-Meteo for forecasting and OpenWeather for geocoding. This required a substantial rewrite of the weather provider logic, including new normalization routines and adjustments to how the gateway determines “local” versus “remote” forecasts. 

The new geocoding function now resolves named locations into coordinates Lyra can reliably use:

```python
async def geocode_location_openweather(query: str, limit: int = 1):
    api_key = os.getenv("OPENWEATHER_API_KEY")
    params = {
        "q": query,
        "limit": limit,
        "appid": api_key,
    }
    async with httpx.AsyncClient(timeout=10.0) as client:
        r = await client.get(OWM_GEOCODE_URL, params=params)
        r.raise_for_status()
        data = r.json()
    return data[0] if data else None
```
And the forecast logic now runs through Open-Meteo in a single, consistently structured pipeline:
```python
async def fetch_open_meteo_forecast(lat: float, lon: float):
    params = {
        "latitude": lat,
        "longitude": lon,
        "hourly": "temperature_2m,precipitation_probability",
        "current_weather": True,
        "timezone": "auto",
    }
    async with httpx.AsyncClient(timeout=10.0) as client:
        r = await client.get(OM_API_URL, params=params)
        r.raise_for_status()
        return normalize_open_meteo(r.json())
```

Testing was performed directly inside the `llm-gateway` container, verifying that geocoding returned correct coordinates globally and that forecasts were sourced from actual provider data rather than model inference. Once the providers were fully operational, Lyra began producing accurate structured weather data.
```bash
$ docker exec -i llm-gateway python3 - << 'EOF'
import asyncio
from weather_provider import geocode_location_openweather

async def main():
    loc = await geocode_location_openweather("Reykjavik")
    print("Result:", loc)

asyncio.run(main())
EOF
Result: {'name': 'Reykjavik', 'lat': 64.145981, 'lon': -21.9422367, 'country': 'IS', 'state': None}
```
With both components operational, Lyra stopped hallucinating remote weather data and started producing accurate responses. This part of the work was successful, the weather pipeline is global.

## Observations  
The surprises came from Lyra’s behavior when trying to present the data.
Despite having access to accurate forecasts, she frequently paraphrased them unpredictably, improvised temporal labels, or ignored tool results and fell back on generic climate expectations. This made it clear that simply improving the data layer isn't enough. The model interprets weather as a topic unless explicitly forced to use the tool output.

Another issue emerged from how environmental context is injected. Including multi-day forecasts in that block caused the model to repeat or remix them in later answers. 

This debugging session also made me relize just how monolithic certain parts of the system still are. The original system prompt and persona python script became an unreadable pile of tooling as more functionality has been added and it continues to carry unrelated responsibilities. Qdrant memory remains unstructured, routing decisions are essentially implicit, and Lyra often behaves like a conversational layer attempting to compensate for missing architecture.

The sytem works, but has grown and needs deliberate structure.

---

## Next Steps  
The next work done will about giving Lyra a coherent architectural foundation. 
The first step is to refactor the gateway into well-defined modules. The current monolithic structure makes reasoning, maintenance, and debugging harder than it needs to be. Breaking the gateway into its components, model client, router, context builder, memory interface, and tool wrappers, will make the entire system more predictable and easier to work on.

Qdrant also needs a real schema. Allowing embeddings to accumulate without structure was fine during early experimentation to show that it works, but Lyra will need to depend on her memory layer for contextual behavior. Establishing collections and payload fields will give her memory some needed structure.

The introduction of the first deterministic tool shows us that routing, weather, tides, local time, and other factual domains must always flow through their respective tools. The model should not be asked to decide whether to call the provider; that decision belongs to the system. The hope is that this will reduce the inconsistencies that surfaced during today's change.

Once routing is in place, the weather chain can be upgraded into a more formal pipeline: location parsing, geocoding, data fetch, normalization, templating, and only then LLM commentary. The result should be that Lyra speaks about the results and doesn't invent them.

Later, a small classification model may be added to refine intent detection. And once the architecture stabilizes, the injection of persona, memory, and environmental context can be made more targeted rather than universal.

Finally, a system-specific evaluation harness will be built to catch regressions automatically. This will allow changes to be validated systematically instead of relying on manual testing and intuition.

This session started off about the weather, but it let me see where Lyra’s architecture has gotten too disorganized to meaningfully continue to grow. The next steps will aim to give her the structure she needs to be reliable, grounded, and, eventually, useful.
